## §1 三条结论（我认可，并核对过事实）

1. **提案的理念层与项目一致**（世界状态=环境真实 / 角色系统=人格真实 / LLM=语言表现）——与「硬状态机管真，LLM 管美」同义，无需改动。
2. **技术栈层整体错配**：提案假定 Web（React/CSS Variables/Pinia/Framer Motion/WebSocket/Three.js/react-virtual/Web Worker）；本项目是 PySide6 单机桌面 → 等价物分别是 QSS / `design_tokens.py` / Qt 信号槽 / `QPropertyAnimation`+`motion.py` / 进程内调用 / QPainter / `QListView` / `QThread`（已有 `LLMWorker`）。**照搬 = 返工**。
3. **换 Web 不做**：动机若是「视觉/分层」→ QML 或 B8 拆包是更近的解；若是「远程访问」→ 那才是产品定位跃迁（数据/Key/运维全变）。**顺序不能错**：B8 拆包（本项目即步 9）→ 再谈上层的任何跃迁。

> 数字校正（对审计文本里的过期值）：全量测试现为 **312**（审计写 305）· `gui.py` 现为 **3713 行**（审计写 3831；SPEC-18 收口再 −309 行）。

## §4 前置声明（任何外部提案交给 Agent 时必须带，本项目起长期生效）

> **本项目是 PySide6 桌面应用，不是 Web 前端。提案中的 React/CSS Variables/Pinia/Framer Motion/WebSocket/Three.js 等技术栈需翻译为 PySide6 等价物：QSS / `design_tokens.py` / Qt 信号槽 / `QPropertyAnimation` / 进程内调用 / QPainter。Design Token 已存在于 `design_tokens.py`（QSS 单一真源 `ui/theme.py`）。组件拆包属 B8（步 9），不在本批。请勿新建 Web 技术栈抽象层。**

## §5 两条必须守住的边界（审计风险 2/3，我加一条机械判据）

1. **情绪表现不得新建真源**：所谓「心情/傲娇值/嘴硬」只能**从 `HardStateEngine` 派生**（favor / independence / recovery / ram_favor / ram_stage）——新建存储 = 复活 A3 死状态。**机械判据**：表现层新增字段必须能指到 `snapshot()` 的既有键，否则拒绝。
2. **第 3–4 层维持 D5「不做」**（Live2D / 房间模式 / 剧情模式 / 背景粒子以外的高表现力项），不因提案漂亮而动摇；唯一例外仍是「长期记忆可视化（暂缓）」与 **D1 立绘复活**。

## §6 待用户确认的两项（其余可自主执行）

- **D6**：是否按本文 §3 的四梯队作为血肉批路线（顺序：骨架批步 7–9 完成后启动第 1 梯队）？——**我的推荐：是**。
- **D7**：字体引入方式 —— ① **子集化打包**（pyftsubset 只留常用汉字+拉丁，文楷≈3-5 MB，EXE 由 57 MB 增至 ~60 MB）② 全量打包（+20 MB 以上）③ 不打包、仅用系统字体栈（现状）。**我的推荐：①**（标题/角色名用文楷，正文留系统黑体——正文可读性更稳且增量最小；三款字体均为 OFL 可自由分发）。
