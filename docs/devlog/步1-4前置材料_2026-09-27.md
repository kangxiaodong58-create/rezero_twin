## 2. F13-2（须确认）：多线程安全 —— 结论：**会跨线程，必须加锁**

**证据（调用链，非推测）**：

```
TwinChatApp._start_vignette（主线程）
  └─ gui.py:2509 class VignetteWorker(QObject)  ← 定义在方法内
       gui.py:2543-2549  thread = QThread(); worker.moveToThread(thread);
                         thread.started.connect(worker.run); thread.start()
       gui.py:2516  _log("引言 Worker.run() 开始")      ← 工作线程内执行
       gui.py:2531  _log(f"引言生成完成: …")            ← 工作线程内执行
       gui.py:2534  _log(f"引言 Worker 异常: …")         ← 工作线程内执行
```

同一文件另有 LLMWorker 走 `moveToThread`（`gui.py:2919-2927`）；其 `run()`（`:450-463`）本身不直调 `_log`，但**同族风险成立**。

**决定**：SPEC-13 实现**必须**给写入加 `threading.Lock`（临界区含 `flush`；durable 档的 `fsync` 同在锁内，临界区为微秒级）。不采用「改用 logging 模块」方案：本 SPEC 是**写入策略**最小改动，换框架会引入格式化/处理器语义差异，超出 L1 边界。

## 3. F13-3（须补充）：atexit 时机与之后调用的兜底

| 问题 | 设计 |
|---|---|
| 注册时机 | **模块导入期**（`_log`/句柄/锁定义之后立即 `atexit.register(_log_close)`）——最早可用，早于任何 `TwinChatApp` 构造 |
| `_log_close` 行为 | 加锁 → `flush` + `close` → 置 `_fh = None` |
| atexit **之后**再调 `_log` | `_log` 内**重开兜底**：`if _fh is None or getattr(_fh, "closed", True): _fh = open(path, "a", …)`（覆盖：崩溃处理器 `gui.py:3771`、解释器收尾期的清理日志） |
| 崩溃处理器路径 | `faulthandler`/`sys.excepthook` 触发的 `_log` 走同一入口 ⇒ 同锁同兜底（**不得**在崩溃路径引入阻塞：锁用 `acquire(timeout=0.5)`，超时则直接放弃本条日志，避免崩溃时死锁） |
