## 1. 产品定位

### 一句话定位

**一座可以走进去的罗兹瓦尔宅邸——蕾姆与拉姆在其中生活、回应你、与你共度时间的桌面角色终端。**

### 不是什么（反例清单）

| 反例类型 | 为什么不是 | 视觉上的错误信号 |
|---------|-----------|----------------|
| 通用聊天软件 | 产品核心是「在场感」与「关系演化」（Rem/Ram 共生→独立的关系结构），不是信息收发效率 | 左右立绘夹消息流的对称双栏 |
| 社交 IM | 不存在多联系人列表、群聊、已读回执焦虑 | 头像 + 昵称 + 气泡的标准 IM 范式 |
| 纯工具仪表盘 | 数据与状态是氛围的一部分，HardStateEngine 的数值是底层逻辑不是展示对象 | 大面积数据卡片、进度条、数值墙 |
| 直播弹幕墙 | 对话是叙事载体，不是流量容器 | 滚动弹幕、礼物特效、观众计数 |
| 桌宠 / 虚拟主播软件 | 角色服务于沉浸，不是卖萌表演 | 常驻循环动画、夸张肢体、悬浮窗拖拽 |
| 养成游戏 HUD | 好感/阶段/锁定是关系状态，不是待填的进度槽 | 顶部好感度条 + 经验条 + 每日任务面板 |

### 是什么

- **角色终端**：打开程序 = 进入一个有角色在场的空间，对话是你与空间交互的方式之一，不是唯一主体。
- **宅邸面板**：界面每一处都在暗示「这是宅邸的某个角落」——走廊、书房、起居室，而不是一个 App 窗口。
- **陪伴界面**：时段、天气、世界事件、记忆都以「宅邸中正在发生的事」呈现，而不是后台数据字段。

> **关键判断线**：如果当前「左蕾姆 \| 中聊天 \| 右拉姆」让用户第一眼读成「双人格聊天机器人」，那就是错的——哪怕暗色精修做得再漂亮。V13 的使命是把隐喻从「聊天壳」切到「宅邸终端」。

## 2. 核心体验（第一眼与五分钟体验）

### 启动后 3 秒内用户应感知到什么

1. **空间感**：我看到的是一个有纵深、有光影的室内场景，不是一个扁平软件窗口。
2. **有人在**：蕾姆与/或拉姆以「正在宅邸中做自己的事」的状态呈现——可能在窗边、可能在整理桌面、可能刚走进画面。不是「待机立绘 + 打招呼气泡」。
3. **时间在流动**：界面的光感、色调、环境线索（窗外天色、灯火强度）暗示当下时段与天气。当前已有「时段 / 天气」世界状态，V13 让它从状态栏文字升级为**环境本身**。

> **反模式警示**：若 3 秒内用户的第一反应是「哦，一个聊天界面，左边蕾姆右边拉姆」，则视觉方向失败。

### 「双子在场」如何被表达

不靠堆特效，靠**空间分配 + 光影叙事 + 信息层级**：

- **空间分配**：双子占据界面不同「区域功能」，而不是对称分列两侧。位置本身传达性格与关系——蕾姆更亲近、更主动对话（前景/近对话区），拉姆更旁观、更偶尔介入（中景/侧位）。这与架构中「Rem 情感救赎 / Ram 战术信任」的分工同源。
- **光影叙事**：主光源从单一方向打来，双子受光面、阴影方向一致，强化「她们真在同一个房间」的错觉。
- **信息层级**：双子状态（心情、在做什么、是否想说话）通过细微视觉线索传达——姿态微变、周围小物变化、光影微调——而不是头顶飘「好感 +1」。当前 CharacterPanel 的好感/阶段/情绪/锁定四件套是数值展示，V13 要把它「去数值化」转译为氛围线索。

### 对话的位置

对话是中心动作之一，但**不是唯一视觉主体**。

对话区应像宅邸中的「一张书桌」或「一处交谈角落」——重要、清晰，但周围还有房间的其他部分。用户可专注对话，也可让程序开着当背景，感受宅邸与双子的存在。当前中栏聊天流 + 80 条 widget 上限的「阅读流」逻辑可保留，但需从「铺满窗口的消息列」降格为「空间中的一个物件」。

## 3. 布局（信息架构 + 线框级）

### 必须批判并避免的默认布局

```
┌──────────┬──────────────────┬──────────┐
│          │                  │          │
│  蕾姆立绘  │    聊天消息流      │  拉姆立绘  │
│          │                  │          │
│          │                  │          │
└──────────┴──────────────────┴──────────┘
        ↑ 当前工程现状（V10.14 三栏）
```

**问题诊断**：
- 对称结构 = 比较结构 = 用户下意识对比谁说得多、谁更主动，破坏「双子一体」的宅邸感。
- 中栏聊天流占主导 = 产品被理解为「双人格聊天机器人」。
- 立绘与对话区割裂 = 角色像贴在窗口两边的装饰，而非空间中的存在。
- CharacterPanel 固定 180 宽、立绘框 240 高，把角色「钉」成左右两根柱子，强化了「框中肖像」而非「房中人」。

> **注意**：批判不是否定现网——V10.14 的暗色精修与 token 体系是扎实底座。批判的是**隐喻**：当前布局把产品锁死在「聊天壳」语义里。V13 允许在保留底座的前提下重新定义空间隐喻。

---

### 方案 A：宅邸起居室（推荐方案）

**核心隐喻**：你坐在宅邸起居室的一张沙发上，蕾姆在你身旁（近景），拉姆在房间另一侧（中景），对话浮现在你们之间的空气中。

**线框示意**：

```
┌─────────────────────────────────────────────┐
│  [ 窗 / 天光 / 时段暗示 ]     [ 壁炉 / 灯火 ] │  ← 环境带：时间 + 天气 + 氛围
│                                             │
│    ╭──────╮                                 │
│    │ 蕾姆  │  ← 近景，偏左，半身/大半身       │
│    ╰──────╯                                 │
│              ╭────────────────────╮          │
│              │   对话与叙事区域     │          │  ← 中景偏右，非全屏宽
│              │   （开场氛围/续聊）  │          │
│              ╰────────────────────╯          │
│                          ╭──────╮           │
│                          │ 拉姆  │ ← 中景偏右 │
│                          ╰──────╯           │
│                                             │
│  ┌─ 今日宅邸 ─┐  ┌─ 事件/记忆入口 ┐  ┌─ 设置 ┐│  ← 底部功能条：宅邸状态
│  └───────────┘  └───────────────┘  └─────┘│
└─────────────────────────────────────────────┘
```

**方案 A 详解**：

| 维度 | 说明 |
|------|------|
| 主视觉焦点 | 蕾姆（近景）——主要交互对象，视觉权重最大；与架构中 Rem 的情感救赎主线一致 |
| 对话区权重 | 中景浮动面板，约占屏幕 40-50% 宽，半透明玻璃质感，融入环境而非割裂 |
| 状态/关系/事件如何「在场」 | 环境带（顶部）暗示时间天气；底部「宅邸状态」条以图标+短句呈现今日事件、双子心情；拉姆的位置与姿态本身就是状态表达 |
| 历史（回忆）进入方式 | 侧滑抽屉式「回忆之书」——从右侧滑入，像翻开相册，按章节/日期组织，不打断主空间（演进自当前 HistoryOverlay 非阻塞浮层思路） |
| 窄屏/最小窗口降级 | 折叠为「单角色 + 对话区」纵向布局，环境带压缩为顶部细条，宅邸状态条收入汉堡菜单；双子可通过 Tab 切换或自动轮替 |

**为什么推荐**：
- 空间感最强，最符合「我在宅邸里」的第一印象。
- 双子位置不对称但平衡，避开对称聊天框反模式。
- 对话区是「空间中的一个物件」，不是「窗口的全部内容」。
- 与现有 HistoryOverlay 非阻塞、SakuraOverlay 粒子分层、SystemLabel 弱化的既有思路同向，迁移阻力相对小。

---

### 方案 B：双子终端（备选方案）

**核心隐喻**：这是一台连接到宅邸的终端屏幕——界面本身是「观测面板」，你通过它看到宅邸中的双子并与之交流。更偏科技感、桌面终端风。

**线框示意**：

```
┌─────────────────────────────────────────────┐
│  ◈ 罗兹瓦尔宅邸 · 终端连接中 ◈   [ 22:47 夜 ] │  ← 顶部状态栏：终端感 + 时间
├──────────┬──────────────────┬───────────────┤
│          │                  │               │
│  蕾姆状态  │   主对话 / 叙事区  │   拉姆状态    │
│  面板     │                  │   面板        │
│  (竖向)   │  开场氛围文字      │  (竖向)      │
│          │  对话流           │               │
│  心情/    │  续聊卡片         │  心情/       │
│  今日活动  │                  │  今日活动     │
│          │                  │               │
├──────────┴──────────────────┴───────────────┤
│  ◇ 宅邸日志  ◇ 世界事件  ◇ 回忆  ◇ 设置      │  ← 底部导航：终端菜单风格
└─────────────────────────────────────────────┘
```

**方案 B 详解**：

| 维度 | 说明 |
|------|------|
| 主视觉焦点 | 中央对话/叙事区，但两侧状态面板有足够视觉重量，形成「终端仪表盘」感 |
| 对话区权重 | 中央约占 55-60%，两侧状态面板持续可见，不断提醒「这是双子系统」 |
| 状态/关系/事件如何「在场」 | 两侧状态面板常驻：当前姿态/心情图标、今日在做什么、关系阶段（用隐喻文字而非数值） |
| 历史（回忆）进入方式 | 底部导航切「回忆」页——整页切换为回忆列表，像终端的不同标签页 |
| 窄屏/最小窗口降级 | 三栏折叠为单栏滚动：顶部双子状态摘要 → 对话区 → 底部导航；状态详情可展开 |

**适用场景**：若产品后期更强调「系统感 / 状态可视化 / 信息密度」，或用户偏好桌面工具美学。

**为什么是备选**：
- 终端感强但「宅邸感」弱于方案 A，更易滑向「仪表盘」反模式。
- 三栏结构与当前现网同构，**迁移成本最低但破局力度也最小**——容易被理解为「只是把现有三栏换了皮肤」，达不到 V13 的隐喻升级目标。

### 方案对比

| 对比维度 | 方案 A：宅邸起居室（推荐） | 方案 B：双子终端（备选） |
|---------|------------------------|---------------------|
| 沉浸感 | ★★★★★ | ★★★☆☆ |
| 信息密度 | ★★★☆☆ | ★★★★☆ |
| 「宅邸」辨识度 | ★★★★★ | ★★★☆☆ |
| 防「聊天软件」误判 | ★★★★★ | ★★★☆☆ |
| 实现复杂度 | 中高（需场景分层） | 中（面板式更常规） |
| 自定义扩展潜力 | 高（场景/房间可换） | 中（面板皮肤可换） |
| 与现网布局差异 | 大（接近重构隐喻） | 小（从三栏演化） |
| 破局力度 | 高 | 低 |

**推荐结论**：V13.0 以**方案 A** 为视觉主方向；方案 B 的状态面板思路可作为 A 的补充元素吸收（如底部「宅邸状态」条的信息组织方式）。若评审认为方案 A 迁移成本不可接受，方案 B 是退路，但需明确标注「这是妥协方向，非首选」。

> **评审纪律（保留意见 3）**：方案 A 是唯一首选，方案 B 仅作成本退路。落地阶段不得默认选 B 偷懒——只有当 V13.2 成本评估具书面报告证明方案 A 迁移成本确实不可接受时，方可启用方案 B，且报告必须附「为何 A 不可行」的具体论证。

### 3.x 技术可行性原则级标注（不写控件实现代码）

> 仅标注「在桌面 Qt/PySide6 技术栈下，各视觉概念是否站得住、依赖什么」，不涉及具体控件与代码。落地方案留到 V13.2。

| 视觉概念 | 可行性判断 | 原则级依赖 / 风险 |
|---------|-----------|-----------------|
| **暗色宅邸基调 + 角色强调色** | 原生可行 | 沿用现有 QSS token 体系，零新依赖 |
| **半透明玻璃质感面板** | 可行但需克制 | Qt 原生无 backdrop-filter；可用半透明 surface + 细边框 + 柔光模拟「玻璃感」，避免依赖 QGraphicsBlurEffect 大面积实时模糊（性能与效果折中） |
| **场景分层 / 纵深** | 可行 | 背景 pixmap 层 + 半透明面板层 + 前景元素层，靠 widget 堆叠顺序实现；现有 LAYER 0-4 约定可演进 |
| **单一方向光源逻辑** | 可行（静态） | 静态受光/阴影靠美术资源烘焙；动态随时段变化的光源切换是 V13.x 增强项，非 V13.0 必做 |
| **环境微动（灯火摇曳 / 尘光粒子）** | 可行 | 沿用 SakuraOverlay 的 QPainter + QTimer 粒子模式；需控制密度与帧率，参照现有 30fps 约定 |
| **角色状态微变（呼吸/眨眼/姿态）** | 静态立绘下受限 | 静态立绘只能靠图层切换/透明度微调模拟；真正的姿态微变依赖 Live2D 或多图层切换——属 L2 远期 |
| **时段/天气环境表达** | 可行 | 世界状态已有时段/天气字段；映射为背景色调/光源色温切换即可，无需新数据通道 |
| **回忆之书侧滑抽屉** | 可行 | 演进自现有 HistoryOverlay 非阻塞浮层；侧滑动画用 QPropertyAnimation |
| **Live2D 动态模型** | 可行但非前提 | 需引入 Live2D SDK 与 Qt 集成；**V13 视觉方向必须在静态立绘下成立**，Live2D 是 L2 加分项 |
| **方案 A 场景化布局** | 可行，迁移成本中高 | 需从「三栏 QHBoxLayout」改为分层场景容器；现有 CharacterPanel / ChatScrollArea 组件可复用但需重组 |
| **方案 B 终端面板布局** | 可行，迁移成本低 | 与现网三栏同构，主要是 token 与组件视觉升级 |

> **原则**：任何「只有引入 Live2D / WebGL / 重型渲染引擎才成立」的视觉方向都不可接受。V13 的核心是空间与氛围，靠 Qt 原生 2D 能力 + 美术资源就能成立。

## 4. 颜色与材质

### 暗色宅邸基调 vs 角色主题色

**分工原则**：
- **宅邸基调（背景层）**：深暖暗色——不是纯黑，而是「夜晚室内、被暖光源照亮的暗色空间」。主基调深棕灰、暗木色、暖灰，营造被包围的安全感。现网 `bg_base #121319` / `bg_surface #1a1b23` 是偏冷的中性暗色，V13 可向暖暗微调，但不必推翻刻度。
- **蕾姆 · 冰蓝（角色强调层）**：用于蕾姆相关交互元素、她的受光面反光、她发起的对话气泡边缘。冰蓝是冷色，在暖暗基调中形成微妙冷暖对比。
- **拉姆 · 蔷薇（角色强调层）**：用于拉姆相关交互元素。蔷薇在暖暗基调中更融入，靠亮度/饱和度区分于背景。

> **关键约束**：角色色永远只做「强调」，不做大面积填充。整个界面主色调仍是宅邸暗色，角色色是其中的光点。这与现网 rem/ram 三件套（accent/bubble/left）「低 alpha 底 + 高 alpha 边线」的策略同向。

### 颜色层级（概念级 Token，非落地值）

```
L0 背景层
  ├── 宅邸底色：深暖灰 / 暗木色（现网 #121319 附近，可向暖微调）
  ├── 空间阴影：更深的暖黑
  └── 环境光溢：来自光源的微弱色溢（顶部天光蓝 / 底部灯火橙）

L1 表面层
  ├── 面板底色：半透明深灰，带轻微玻璃质感（演进自 bg_surface / surface_2）
  ├── 卡片底色：比面板略亮，有细边框
  └── 悬浮元素：最亮表面层，带柔光边缘

L2 内容层
  ├── 主文字：暖白（非纯白，带一点黄调；现网 text_primary #E2E8F0 可微调）
  ├── 次文字：中灰（text_secondary #94A3B8）
  ├── 辅助文字：暗灰（text_muted #64748B），用于时间戳/状态标签
  └── 边框/分割线：极低透明度白或角色色（border_subtle 0.08 / border_focus 0.15）

L3 强调层
  ├── 蕾姆冰蓝：rem_accent 附近（交互、她的对话标识）
  ├── 拉姆蔷薇：ram_accent 附近（交互、她的对话标识）
  ├── 系统/宅邸：暖金色（现网 accent #c9a96e 附近，宅邸状态、系统提示）
  └── 警示/特殊：低饱和红或紫（锁定、失忆等异常状态）
```

### 主材质隐喻：灯火玻璃

从「玻璃 / 纸质 / 灯火 / 走廊」中选 **「灯火玻璃」** 为主隐喻：

- **玻璃**：对话面板、状态卡片用半透明质感，让背后宅邸场景隐约可见——强化「面板悬浮在空间中」。现网已有 `rgba(255,255,255,0.03~0.06)` 表面叠加（Design System V1 建议收敛为 SURFACE_TINT），V13 延续此方向。
- **灯火**：整个界面光源逻辑是「被几盏灯照亮的暗室」——有明确主光源方向、光晕、暖色溢。不是均匀发光的屏幕。
- **纸质**：仅用于「回忆之书」「宅邸日志」等特定叙事元素，作为次级材质，不与主隐喻争锋。

**为什么不选其他**：纯纸质太扁平缺深度；纯走廊太具象限布局；大杂烩视觉语言不统一显廉价。

### 与现有 V1 Token 的衔接原则

- **保留**：暗色基调、rem 冰蓝 / ram 蔷薇的角色色身份、token 化思路、四级背景明度递进。
- **演进**：从「扁平暗色 UI」演进为「有光源、有空间、有材质的暗色场景」。补齐 V1 缺口（FONT / DIMENSION / SURFACE_TINT / 统一 ROLE_COLORS）正好是 V13 落地的前置工作。
- **不要求**：逐 key 对齐现有代码 token——V13 是视觉方向预研，token 精确映射是 V13.1/V13.2 的工作。

## 5. 动效原则

### 总原则：克制 · 服务沉浸 · 像呼吸一样自然

动效目的是**让宅邸感觉活着**，不是**让用户觉得动画很酷**。产品是「长期陪伴」不是「三分钟惊艳」——动效太花会快速疲劳。

### 允许的动效类型与频率

| 动效类型 | 用途 | 频率上限 | 时长参考 |
|---------|------|---------|---------|
| 环境微动 | 灯火摇曳、窗外微光、窗帘极轻飘动 | 持续但极慢 | 周期 > 10s，幅度 < 5% |
| 角色状态微变 | 呼吸感、眨眼、姿态微调（若有立绘分层） | 低频随机触发 | 单次 < 2s，间隔 > 30s |
| 入场动效 | 启动时元素渐次浮现、对话面板滑入 | 仅启动/切场景 | 整体 < 1.5s |
| 状态变化反馈 | 好感阶段变化的光影微变、新事件轻提示 | 事件驱动 | 单次 < 1s |
| 轻粒子 | 萤火、尘光、极少量飘散粒子 | 常驻低密度 | 同时可见 < 10 个 |
| 对话入场 | 新消息淡入 / 轻微上浮 | 每条一次 | < 300ms |

> 现网 SakuraOverlay（30fps / 5 色粒子）是可复用的粒子底座，但需降密度并向 ram 蔷薇色相靠拢，强化「樱花/拉姆」语义而非独立硬编码色。

### 明确禁止

- 常驻循环卖萌动画（甩头发、比心）——这是桌宠，不是宅邸中的人。
- 遮挡阅读的动效（任何挡住对话文字的动画/粒子/特效）。
- 高频闪烁、色彩频闪。
- 强制注意力的弹窗动画（弹跳、抖动、放大缩小）。
- 全屏特效刷屏（好感升级烟花、彩带、全屏光效）——破坏沉浸。

### 视觉权重差异

| 元素类型 | 视觉权重 | 动效强度 |
|---------|---------|---------|
| 开场氛围 / 叙事文字 | 最高 | 较慢逐字浮现 + 环境光变化，营造仪式感 |
| 角色对话 | 高 | 淡入 + 轻微位置偏移，自然不突兀 |
| 续聊卡片 / 话题建议 | 中 | 轻弹入 + 微光，引导但不强迫 |
| 系统轻提示 | 低 | 极小图标变化 + 极淡文字，像宅邸里一声轻响（演进自 SystemLabelWidget transient 机制） |
| 状态 / 数值变化 | 最低 | 几乎不可见渐变，用户「感觉有变化」但不被打断 |

## 6. 自定义系统（范围说明书级）

### 分层定义

#### L0 · 默认（V13 必做）

官方宅邸主题，开箱即用。

- 一套完整「罗兹瓦尔宅邸 · 夜间起居室」默认场景。
- 官方蕾姆 / 拉姆立绘（或当前工程使用的角色形象）。
- 默认主题色（冰蓝 / 蔷薇 / 暖金）。
- 默认动效强度（中等，符合第 5 节原则）。

> L0 目标：用户第一次打开就获得完整、设计过的沉浸体验，不需要任何设置。

#### L1 · 用户可调（V13 建议做）

用户在不破坏整体视觉语言前提下可调的参数。

| 可调项 | 调整范围 | 约束 |
|-------|---------|------|
| 背景场景 | 官方提供 2-3 个宅邸场景切换（起居室 / 书房 / 走廊） | 场景必须符合宅邸世界观，V13 阶段不允许用户传任意图做背景 |
| 角色立绘 | 官方提供不同姿态 / 服装切换 | 必须保持光源一致性，不允许随意替换导致光影穿帮 |
| 主题色微调 | 角色色饱和度 / 亮度微调（±20%） | 不允许改色相——冰蓝还是冰蓝，蔷薇还是蔷薇 |
| 动效强度 | 低 / 中 / 高三档，或完全关闭 | 低档 = 仅必要交互反馈；高档 = 环境动效全开 |
| 字体大小 | 对话区文字 3 档 | 不影响布局结构（呼应 V1 缺的 FONT token） |

#### L2 · 后期增强（V13 不做，仅标记）

| 项目 | 说明 | 时间预期 |
|------|------|---------|
| 布局皮肤包 | 完全不同的布局隐喻（如方案 B 终端风皮肤） | V13.x 后期 |
| Live2D 支持 | 角色从静态立绘升级为 Live2D 动态模型 | 远期，依赖技术预研 |
| 用户自制场景 | 允许用户导入背景图 + 自定义光源参数 | 远期，需编辑器 |
| 语音 / 音效系统 | 环境音、角色语音自定义与音量控制 | 与音频系统同步规划 |

### 自定义的红线

1. **不能破坏信息层级**：用户再怎么调，对话区可读性、状态信息可发现性不能被破坏。
2. **不能破坏光源逻辑**：角色与场景光源方向必须一致——这是「她们真在这个空间里」的底线。
3. **用户资源缺失时的回落**：任何自定义资源加载失败，必须静默回落到 L0 默认，不允许「图片裂了」「空白面板」。
4. **世界观一致性（建议）**：官方自定义内容应保持 Re:Zero 世界观内一致——V13 阶段不搞赛博朋克蕾姆、不搞泳装拉姆。

## 7. 组件与状态的可视化语言

> 本节概念级说明，不涉及具体控件实现。

### 对话气泡 vs 系统轻提示 vs 开场氛围

三种完全不同视觉权重的元素，必须在视觉语言上明确区分：

| 类型 | 视觉特征 | 出现时机 | 设计意图 |
|------|---------|---------|---------|
| 开场氛围 / 叙事文字 | 全屏或大面积文字，低对比度，缓慢浮现，可能伴随环境光变化 | 启动、进入新场景、重大剧情节点 | 建立氛围，让用户「进入状态」 |
| 角色对话气泡 | 半透明玻璃面板，有角色色边缘光晕，文字清晰可读 | 角色说话时 | 主要交互内容，清晰但不突兀（演进自 BubbleWidget + 角色色左边线策略） |
| 系统轻提示 | 极小图标 + 极淡文字，出现在角落或状态条 | 保存成功、连接状态、后台事件完成 | 告知但不打扰，像宅邸里一声轻响 |

**绝对禁止**：把系统提示做成和对话气泡一样大的弹窗。宅邸里不会突然蹦出 Windows 风格提示框。

### 好感 / 阶段 / 锁定 / 失忆的可视化

**核心原则：可感知，不可计数——但仅限主路径。**

现网 CharacterPanel 直接展示好感数值 + 阶段 + 情绪 emoji + 锁定标记——这是「数值墙」。V13 要把它转译为氛围线索。「不可计数」约束的范围与边界（保留意见 1、2）：

- **主路径（主界面）**：禁止数字、进度条、经验条。状态以氛围线索呈现（姿态/光感/称呼/物件）。关系阶段中文名也不在主界面常驻，避免与氛围线索重复。
- **次级路径（回忆之书章节、宅邸日志、按需唤起的诊断面板）**：允许出现关系阶段中文名（「初识/熟悉/信赖/？？？」）作为叙事锚点；这是「可感知」的延伸，不违反「不可计数」。
- **诊断通道（非侵入、按需唤起）**：必须存在一条隐藏的、不破坏沉浸的通道，可查看精确状态（好感数值、独立度、阶段、Loyalty Lock / 失忆等风险标记），供调试与深度查看。诊断通道不得常驻主界面，唤起方式可为角落机关 / 快捷键 / 右键菜单，与「设置入口藏起来但找得到」同逻辑。

> 原则：主界面负责「感觉」，诊断通道负责「事实」。两者并存，互不越界。

| 状态 | 可视化方式 | 反模式（禁止） |
|------|-----------|--------------|
| 好感阶段 | 角色姿态变化、对话距离感、称呼变化、场景小物件（如她为你泡的茶） | 顶部「好感度 73%」进度条 |
| 关系阶段 | 隐喻性章节标题 / 关系描述（「初识」「熟悉」「信赖」「？？？」） | 等级数字 + 经验条 |
| 锁定内容 | 视觉上「门是关着的」「书页是空白的」「房间是暗的」——空间隐喻 | 灰色锁图标 +「VIP 解锁」 |
| 失忆 / 异常状态 | 画面整体色调变化（偏冷/偏灰）、文字轻微模糊、角色位置不确定 | 红色警告条 + 错误代码 |

> 与架构呼应：HardStateEngine 仍负责精确数值与风险控制（Loyalty Lock、Independence Adjuster、Oni Stage），数值在底层不变；V13 改变的是**数值如何被呈现**——主界面氛围转译，诊断通道按需直读。底层逻辑零改动，诊断通道只是开了另一扇读底层快照的窗。

### 世界状态如何进入主界面

世界状态（时段、天气、事件、地点感）不应被塞进状态栏，而应**融入环境本身**：

- **时段**：通过整体光感、光源色温、窗外天色表达。清晨偏冷蓝，黄昏偏暖橙，深夜深蓝 + 灯火。
- **天气**：窗外视觉线索（雨丝、雪、阳光）+ 极轻微环境动效。不做天气图标。
- **事件**：宅邸中细微变化——桌上多一封信、壁炉烧得更旺、灯多亮几盏。同时底部状态条有文字提示。
- **地点感**：通过背景场景本身表达——你在起居室、书房、走廊。切换场景 = 切换地点。

> 设计目标：用户不用看任何文字，光看画面光和颜色，就能大致猜出「现在是晚上，好像在下雨，蕾姆在我旁边」。

## 8. 非目标（Non-goals）

V13.0 预研阶段 **明确不做**：

1. **不实现代码**：本阶段只产出概念与规范文档，不写 PySide6 代码，不改 `gui.py`，不出具落地任务书。
2. **不做成开放世界地图点击**：产品不是「点击宅邸各房间进入不同功能」的 AVG，场景切换是氛围变化，不是玩法核心。
3. **不强制绑定 Live2D**：V13 视觉方向必须在静态立绘条件下成立。Live2D 是加分项，不是前提。
4. **不复制某款手游 UI**：不像素级参考任何现有游戏 / 软件。视觉语言必须为这个产品量身定义。
5. **不做社交功能**：没有好友、分享、社区、排行榜——这是一个人的宅邸。
6. **不做多角色扩展**：V13 只考虑蕾姆 + 拉姆双子的视觉架构，不预留「未来加 10 个角色」的通用框架。
7. **不做移动端适配**：V13 是桌面端视觉预研，不考虑手机 / 平板布局。
8. **不做主题商店 / 付费皮肤**：V13 阶段不谈商业化，自定义系统只谈能力不谈变现。
9. **不做语音 / 音效设计**：音频是另一个维度，V13 只负责视觉。
10. **不做性能优化方案**：落地阶段再考虑渲染性能、内存占用。
11. **不改系统架构与业务逻辑**：状态机、Prompt、Validator、ConversationStore、LLM Bridge、世界状态——一律不碰。V13 是 UI/视觉层预研。

## 9. 对开发方向的反向约束（重要）

> 视觉方向不是「给功能套个皮」，而是「定义产品应该长什么样，然后功能往这个方向长」。
>
> 如果采用本视觉方向，后续功能设计必须接受以下约束——**功能服务于视觉定位，而不是视觉迁就功能列表。**

### 9.1 主动性：角色主动找你，而不是你点按钮触发

- **视觉约束**：宅邸界面中，双子状态变化、主动发起的对话、环境事件线索，都是「被动感知」的——用户不用点任何东西就能感觉到。
- **开发含义**：主动性系统（角色主动搭话、事件触发、时间推进）应是产品核心机制之一，而非附加功能。不能做成「用户点『主动对话』按钮 → 角色说一句话」的按钮式交互。
- **反例**：界面一排「闲聊」「讲故事」「玩游戏」「查看好感」按钮——把宅邸变成功能菜单，视觉再美也救不回来。

### 9.2 场景：一切发生在宅邸中

- **视觉约束**：所有功能都需要有「宅邸中的对应物」。设置 = 书桌上的机关盒；回忆 = 书架上的相册；事件 = 桌上的一封信；帮助 = 宅邸管家手册。
- **开发含义**：新增功能时先想「这个功能在宅邸里是什么东西？放在哪？怎么被发现？」，而不是「这个按钮放哪？」。
- **反例**：设置面板是标准 Windows 风格选项卡窗口——直接打破所有沉浸感。

### 9.3 历史：回忆是珍贵的，不是聊天记录

- **视觉约束**：历史对话以「回忆之书」「宅邸日志」等叙事化形式呈现，有章节、有温度，而不是按时间倒序的消息列表。
- **开发含义**：历史 / 记忆系统设计应有筛选、有重点、有叙事组织，而不是简单「全部聊天记录导出」。现网 HistoryOverlay 已是非阻塞浮层 + 搜索 debounce 的好底子，方向对，但「列表」语义需升级为「书」语义。
- **反例**：标准聊天记录搜索框 + 分页列表——这是微信，不是宅邸回忆。

### 9.4 设置入口：藏起来，但找得到

- **视觉约束**：设置入口不应是界面上最醒目的按钮之一。它应是宅邸中的「小机关」——不仔细看看不到，但想找时找得到。
- **开发含义**：设置功能是「需要时才用」的工具，不应占据主界面视觉重心。可放角落、可藏右键菜单、可是不起眼图标。
- **反例**：顶部工具栏一排大图标：文件 / 编辑 / 视图 / 设置——标准软件范式，完全不符合角色终端定位。

### 9.5 信息密度：宁可少，不可乱

- **视觉约束**：宅邸界面信息密度应是「一个房间里能自然放下的信息量」。不能像仪表盘堆满数据卡片。
- **开发含义**：若有很多状态数据想展示，应分层——默认只显示最核心的，深入查看时再展开。不能一上来把所有数值铺桌面。
- **反例**：主界面同时显示好感度、心情值、体力、饥饿、亲密度、信任度、今日事件列表、记忆条数——这是养成游戏 HUD，不是陪伴界面。

### 9.6 数值与呈现分离

- **视觉约束**：HardStateEngine 的精确数值（好感、独立度、阶段）是底层事实，但**不应直接暴露在主界面上为数字**。诊断通道例外（见 §7、保留意见 1）——按需唤起时可直读底层快照。
- **开发含义**：架构上保持「数值层（HardStateEngine）↔ 转译层 ↔ 呈现层」的三段式。数值层照常精确运算；转译层把数值映射为氛围线索（姿态/光感/称呼/物件）；主呈现层只显示氛围线索，诊断通道另开一窗读底层快照。这样既不损失系统精度，又不在主界面泄露冷数值。
- **反例**：CharacterPanel 直接把 `好感: 73` `阶段: 信赖` 当文本贴出来——把底层事实当成了展示对象。

### V13.3 ~ V13.x：分阶段落地（假设进入落地）

建议落地顺序（从核心到外围）：

2. **角色呈现与对话区**：双子在场景中的位置、姿态、对话面板玻璃质感。核心交互闭环。
3. **状态可视化**：宅邸状态条、世界状态环境表达、好感/阶段的隐喻式呈现（数值转译层）。
4. **回忆与历史**：回忆之书的视觉与交互（演进自 HistoryOverlay）。
5. **自定义系统 L1**：场景切换、立绘切换、主题色微调、动效强度。
6. **动效精修**：环境微动、角色状态微变、粒子系统（演进自 SakuraOverlay）。
7. **细节打磨**：边缘情况、窄屏适配、性能优化。

> **重要前提**：以上分期仅为视觉方向规划建议，不构成开发任务书。是否进入落地、何时进入落地，由产品决策另行确定。**V11.8 验证期优先**——先真用、后视觉；本文是方向锚，不是现在开工令。

## 设计决策记录

| 决策 | 选择 | 理由（1-2 句） |
|------|------|---------------|
| 主布局方案 | 方案 A：宅邸起居室（推荐） | 空间感与沉浸感最强，最能区分于「聊天软件」，符合「打开程序 = 进入宅邸」的产品定位 |
| 备选定位 | 方案 B：双子终端（妥协退路） | 与现网同构迁移成本低，但破局力度小、易被读成「换皮三栏」，仅作成本不可接受时的退路 |
| 主材质隐喻 | 灯火玻璃 | 玻璃提供「面板悬浮在空间中」的层次，灯火提供暖暗基调光源逻辑，二者结合既有深度又不喧宾夺主 |
| 角色色使用策略 | 仅做强调层，不大面积填充 | 角色色是「光」不是「漆」——在暖暗宅邸中，冰蓝和蔷薇是点亮空间的光点，而非涂满界面的油漆 |
| 动效强度定位 | 克制、低频、服务沉浸 | 产品是「长期陪伴」不是「三分钟惊艳」——动效太花会快速疲劳，像呼吸一样自然的微动才经得起长时间相处 |
| 自定义范围 | L0 默认 + L1 微调，L2 远期 | V13 阶段先把默认体验做到极致，自定义是锦上添花不是雪中送炭；范围爆炸会拖垮核心体验质量 |
| 状态可视化原则 | 可感知，不可计数；数值与呈现分离 | 数值化状态面板会把陪伴关系变成养成游戏；HardStateEngine 数值在底层保留精度，呈现层只显氛围线索，系统精度与沉浸感兼得 |
| 非目标中排除 Live2D 依赖 | 静态立绘也必须成立 | 视觉方向核心是空间与氛围，不是角色动起来；若只有静态立绘就不像宅邸，说明方向本身有问题 |
| 反向约束开发的必要性 | 专门一节强调 | 视觉方向若只是「套皮」，最终产品仍会滑回聊天软件；必须从功能设计层面就接受「宅邸逻辑」约束 |
| 技术可行性原则 | Qt 原生 2D 能力必须独立成立 | 任何「只有引入 Live2D / WebGL / 重型渲染引擎才成立」的方向都不可接受；保证桌面端轻量与可落地 |
| 主路径与诊断通道并存 | 主界面氛围化 + 隐藏诊断通道（保留意见 1） | 主界面负责「感觉」，诊断通道负责「事实」；既不破坏沉浸，又不丢失系统可观测性，避免氛围化走极端变成黑盒 |
| 「不可计数」边界 | 仅限主路径，次级界面允许阶段中文名（保留意见 2） | 主界面彻底去数字保沉浸；次级界面用阶段中文名作叙事锚点，兼顾「可感知」与「可追溯」 |
| 方案 A/B 评审纪律 | A 唯一首选，B 仅成本退路且需书面论证（保留意见 3） | 防止落地阶段以「迁移成本」为借口退回舒适区，导致 V13 破局目标落空 |
| 落地前置门禁 | V13.2 报告为硬前置，本文非开工令（保留意见 4） | 强制冲突与成本评估先于代码落地，避免方向未验证即动工造成返工 |
