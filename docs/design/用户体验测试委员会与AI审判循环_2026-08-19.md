# 用户体验测试委员会 × AI 产品审判循环 · 本项目落地研判

> 日期：2026-08-19 ｜ 依据：用户提案《推荐测试 Agent 架构》+ 项目现状实测（V14.4 / 88 pytest / 真机验收报告 / 内容密度研判报告）
> 结论一句话：**框架立意正确，但本项目缺的不是「更多测试」，而是把已有的散件——案例库、验收报告、pytest——组装成可重复、可回归、有成本纪律的审判循环。建议裁剪为「三委员会 + 双轨评审 + 版本门禁」，并新增人设指纹、黄金剧本、成本金字塔三项机制。**

---

## 0. 对框架本身的研判（哪些用、哪些改）

| 框架要素 | 研判 | 本项目处理 |
|---|---|---|
| 六 Persona | ✅ 方向正确，但**六人格对单产品过重**——审判成本会超过收益 | 裁剪为**三委员会**（见 §2），Persona 合并：小白+UX 专家+PM → UX 委员会；目标用户+挑剔用户 → 角色委员会；压力测试 → 压力委员会 |
| 四 Phase（盲测/任务/破坏/满意度） | ✅ 全保留，但**盲测对象要修正** | 本项目盲测的真正关卡不是「不知道产品」，而是**拿到 EXE 后首启**：配 Key、找入口、第一个问题怎么问——这是小白唯一会退出的地方 |
| S/A/B/C 台账 | ✅ 完全保留，项目已有先例 | 统一进 `docs/evaluation/` 台账模板（对齐 2026-08-06 验收报告 P0/P1/P2 口径） |
| 审判模式（禁止夸奖） | ✅ 保留 | 补一条铁律：**每条问题必须带可复现的输入序列**，否则「具体/可复现/可执行」是空话 |
| 审判循环（开发→测试→…→修复→重测） | ✅ 正确 | **补上框架缺失的「回归」维度**：单次审判价值有限，版本间 diff 才有意义——本项目 V13/V14 历史证明，体验退化（帝国篇 OOC）比新功能 bug 更致命 |

**框架的三个盲区（本项目必须自补）：**

1. **成本维度缺失**：LLM 产品测试消耗 API 预算。必须做成本分层金字塔（§3），否则审判循环会烧钱烧到跑不动。
2. **回归维度缺失**：框架是一次性审计思维。需要「黄金剧本 + 人设指纹」让体验可对比、可防退化（§4）。
3. **长期使用维度缺失**：陪伴类产品的核心是记忆可信度，这需要**跨天/跨周模拟**——靠时钟加速而非真等（§5.4）。

### 已有资产（比框架假设的好得多）

| 资产 | 位置 | 说明 |
|---|---|---|
| 规则层测试 | `tests/` 7 文件 88 用例 | 状态机/好感/来信/撤回/引用/搜索/UI offscreen/LLM 失败注入，**零 API 为主**——这是 L0 金字塔底座 |
| 角色测试案例库 | `docs/evaluation/test_cases.md` | Phase 0-7（人格/关系/灵魂/互动/压力/世界/红队）——**已是 Persona 剧本雏形** |
| 真机验收 | `docs/audit/2026-08-06_product_acceptance_v12.md` | 26 次真实调用 ¥0.0661，六维评分表，P0/P1/P2——**已有审判报告模板** |
| 内容密度研判 | `docs/design/场景化内容密度…2026-08-19.md` | Step 0-5 路线图，v14.4 已完成 Step 0——**已有可复现的缺陷发现方法论** |

### 缺口（审判循环要补的）

1. **没有「可重复执行的体验剧本」**：案例库是给人工看的清单，不是可反复跑的脚本；两次审判之间无法对比。
2. **没有体验回归机制**：V13→V14 谁保证角色「没变冷/没变油」？目前靠印象，不靠数据。
3. **没有版本门禁**：发布前只过 pytest（规则轨），情绪轨无人把关。
4. **已知雷区无台账**：首启 Key 关卡、字号 11px、流式无超时（验收 P0 遗留）、括号体密度、gui.py 3003 行——散在报告里，未成持续跟踪的 S/A/B/C 列表。

## 2. 落地架构：三委员会 + 双轨评审

```
               版本发布前 · 审判关卡
                        │
        ┌───────────────┼───────────────┐
        ↓               ↓               ↓
   角色委员会         UX 委员会       压力委员会
 (原作粉+挑剔用户)  (小白+UX专家+PM)  (压力用户)
        │               │               │
   黄金剧本(Phase0-7)  首启盲测+4任务    破坏矩阵+时钟加速
   情感曲线探针        满意度问卷        性能采样
        └───────────────┼───────────────┘
                        ↓
              双轨评审（每条问题都过两轨）
        规则轨（客观可断言） │ 情绪轨（语感可统计）
                        ↓
             S/A/B/C 台账（问题模板化）
                        ↓
        开发修复 → 重审（S 级清零才算过门禁）
```

### 三委员会定位

| 委员会 | 合并的 Persona | 核心问题 | 主要资产 |
|---|---|---|---|
| **角色委员会** | 目标用户（原作粉）+ 挑剔用户（对标 Character.AI / 星野 / 米哈游 UI） | 「喜欢蕾姆/拉姆的人，会不会觉得它是真正陪伴角色？」 | 黄金剧本 + 人设指纹 + 情感曲线 |
| **UX 委员会** | 小白 + UX 专家 + 产品经理 | 「第一次打开能不能不用说明书完成核心体验？」「这功能用户真的需要吗，还是开发者自嗨？」 | 首启盲测 + 4 任务测试 + 满意度问卷 |
| **压力委员会** | 压力测试用户 + 极端挑剔用户 | 「连用 30 分钟、高频操作、大存档，会不会崩/卡/混乱？」 | 破坏矩阵 + 时钟加速 + 性能采样 |

### 双轨评审（本项目的核心创新点之一）

每条发现的问题同时过两轨：

- **规则轨（客观、可自动断言）**：状态数值正确性、模板命中率、OOC 词表、格式校验、越界拦截——**pytest 化**，任何人重跑结果一致。
- **情绪轨（语感、可统计化）**：括号体密度、AI 味词频、称呼一致性、情感极性、主动句比例——**抽成指标脚本**，用数字而非印象说话（见「人设指纹」）。

## 3. 成本金字塔（框架盲区 #1 的解法）

| 层 | 内容 | 成本 | 现状 |
|---|---|---|---|
| **L0 零 API** | 状态机/模板/校验器/UI offscreen/失败注入 | ¥0 | ✅ 88 用例，已达标 |
| **L1 微成本** | local 模板模式端到端跑黄金剧本（确定性输出） | ¥0 | ⚠️ 部分可行，需补「剧本驱动」入口 |
| **L2 真机** | LLM 真实调用跑剧本 + 审判问卷 | **预算封顶 ¥2/次** | ✅ 已有 ¥0.066 先例 |

**纪律**：审判循环默认跑 L0+L1；只有版本门禁、重大改版、S 级争议才开 L2。L2 每次审判记录 token 与花费（沿用验收报告口径），防止「审判烧钱 > 修 bug 省钱」。

## 4. 三项新增机制（相对原框架的创新）

### 4.1 人设指纹（Persona Fingerprint）——把「角色一致性」变成可测试指标

对每个角色自动统计一组可复现指标，形成指纹快照，版本间对比漂移：

```
指纹指标 v1（建议 8 项）：
  称呼一致性       —— 蕾姆自称为「蕾姆」的命中率（不得用「我」）
  行动/台词比     —— 「（动作描写）」占比（验收报告指出偏密，目标 ≤30%）
  AI 味词频       —— 「毕竟/其实/或许/无论如何」类词的每千字频次
  情感极性分布    —— 正向/负向/中性句比例（关系阶段应有可测量差异）
  主动句比例      —— 提出话题/反问的比例（拉姆被动化检测）
  毒舌率          —— 拉姆挖苦句占比（低好感应显著高于高好感）
  自卑表达率      —— 蕾姆「替代品/配不上」类表达随独立度下降
  称呼对象漂移    —— 是否称呼用户为已记录的 user_name
```

**用法**：黄金剧本跑完后自动生成指纹 → 与上一版本 diff → **漂移超过阈值（如 >15%）自动标记为 A 级问题**，进台账。这解决了「V13→V14 角色变没变」的玄学问题。

### 4.2 黄金剧本（Golden Sessions）——体验回归的基线

把 `test_cases.md` Phase 0-7 改造为**固定输入序列 + 固定观测点**的剧本文件（JSON/MD），每次审判跑同一套：

- **剧本 = 可复现性的载体**：任何问题报告都引用 `剧本ID + 第N轮`，杜绝「我随便试了试发现…」
- **三套剧本**：`script_character.md`（角色委员会）/ `script_ux.md`（首启+4任务）/ `script_stress.md`（破坏矩阵）
- **存档**：每次审判的完整 transcript 存 `docs/evaluation/sessions/<版本>_<日期>/`，供版本间 diff 与复查

### 4.3 情感曲线探针（情感弧线验证）

在角色剧本里埋 6-8 个情绪探针（关键节点输入），对每个探针回复做情感极性打分，画成曲线：

```
期望曲线：陌生(中性偏负) → 熟悉(正) → 信任(正高) → 深爱(正高+忠诚锁定)
异常形态：直线（无成长感）/ 突跳（升温过快）/ 回退（忠诚锁定失效）
```

这直接验证项目核心主张——「关系是有结构的，而非单纯好感加减」——把 README 里的设计原则变成可断言的东西。

### 4.4 时钟加速模拟

来信、日更问候、记忆恢复、离线桶这些「跨天机制」，真等会拖死审判循环。方案：

```
pytest 级：直接构造 WorldState/时间戳（现有 test_letter_manager 已这么做）
真机级：   L2 审判时用 system time 模拟或构造存档（修改 memory.json 的 last_* 字段）
```

**刻意不做**：不 mock 系统时钟进 GUI 自动化（Qt 全局时间劫持风险大，收益低）——跨天场景一律走「构造存档」而非「等时间」。

### 4.5 使用痕迹审计（真实数据驱动）

开发者的真实 `data/conversations.db` 就是免费的 UX 语料：

- **撤回率/删除率**：用户主动撤回/删除的轮次 → 体验断点高发区
- **搜索失败率**：搜了但零命中的关键词 → 记忆系统可信度线索
- **来信跳过/回应率**：主动来信有没有被接住、被删除
- **断会话时长分布**：多久没回来 → 留存信号

每次审判附带一次痕迹统计，作为「用户不会说出口的反馈」。

### 4.6 对标审判（差异化定位）

挑剔用户人格不只挑毛病，还要回答框架里那个灵魂问题：**「为什么选你而不是 Character.AI / 星野 / Glow？」**

本项目候选差异化答案（需审判验证）：
1. **双子结构**：双角色互动、姐妹关系状态机——单角色产品没有
2. **硬约束×软表达**：好感/关系有真实成长结构，不是聊一天就「永远爱你」的廉价甜蜜
3. **世界观内化**：现代话题被角色视角消解（验收报告 GIL 测试是教科书案例）
4. **零 API 也可玩**：本地模板模式——对白嫖用户是真实卖点

对标审判产出「差距清单」：哪些维度被商业产品碾压（如 UI 精致度、语音、多端同步），哪些是护城河，哪些「不需要赢」。

## 5. 阶段目标任务（每步可独立验收）

### Phase 0：搭台子（建议本周）
| 任务 | 产出 | 验收 |
|---|---|---|
| 台账模板 | `docs/evaluation/issue_tracker.md`（S/A/B/C + 【问题】【用户感受】【影响】【复现方式】【修改建议】【预计提升】+ 双轨标记 + 状态列） | 模板被第一条真实问题使用 |
| 剧本化改造 | `docs/evaluation/sessions/` 目录 + 三套剧本 v1（角色剧本=现有 Phase 0-7 转固定序列；UX 剧本=首启+4 任务；压力剧本=破坏矩阵清单） | 剧本可被独立 agent 照做执行 |
| 人设指纹 v1 | `tools/persona_fingerprint.py`（8 项指标，读 transcript 输出指纹 JSON） | 对 V14.4 存档能出数，两次跑同结果 |
| 已知雷区入台账 | 流式超时/字号 11px/括号体密度/首启 Key 关卡等 6-8 条历史问题转台账 | 台账有可跟踪的初版 |

### Phase 1：第一轮审判（三个委员会各跑一次）
- **角色委员会**：跑角色黄金剧本（L1 本地模式 + 可选 L2 真机），出指纹基线 + 情感曲线 + 对标差距清单
- **UX 委员会**：EXE 首启盲测（不喂 README）+ 4 任务测试 + 满意度问卷模拟
- **压力委员会**：破坏矩阵（误操作/长对话 500 条/大存档/时钟加速）+ 性能采样
- **验收**：产出第一版台账，S 级清零，A 级全部有修复方案

### Phase 2：回归机制化
- 黄金剧本存档 + 指纹基线入库（`docs/evaluation/baselines/`）
- **版本门禁脚本** `tools/trial_gate.py`：pytest 全绿 + 剧本 diff + 指纹漂移阈值 → 输出「通过/拦截」
- **验收**：模拟一次「故意引入角色漂移」被门禁拦截（门禁自测）

### Phase 3：审判循环制度化
- 把「审判模式」沉淀为**可复用 DSH 技能**（skill：`ux-trial-committee`，系统无关：给定产品 → 三委员会审判 → S/A/B/C 台账）——这一步同时服务 Re:Zero Twin / Hermes Agent / DeepSeek Harness 三个系统
- 版本发布流程加审判关卡：`开发 → pytest → 三委员会审判 → 台账 → 修复 → 重审（S 清零）→ 发布`
- **验收**：V15.0 发布走完一次完整循环，台账可追溯

## 7. 刻意不做（防扩权）

- 不开发独立 GUI 测试框架（Qt offscreen 已够，Playwright 级投入对单机软件不划算）
- 不为审判开发产品内功能（审判是开发流程的一部分，不是产品功能）
- 不做真人用户招募/埋点（个人项目阶段，用痕迹审计 + Agent 模拟代替）
- 审判模式技能不做成「无限自我批判」——**每次审判必须带修复方案**，禁止只挑刺不给出路
