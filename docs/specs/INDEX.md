# SPEC 台账（唯一索引）

> **SPEC 全文**：`docs/specs/SPEC-<ID>-<简述>.md`——一个 Spec 一个文件，直接打开即可审计，不需要翻聊天记录。
> **状态机**：`待批准 → 已批准 → 执行中 → 已完成 / 已回滚 / 已放弃`
> 对话里的批准口令一律是 `批准 [L0] SPEC-<ID>`；未收到口令前，agent 不得改动任何文件。

## SPEC 的核心价值（Agent 视角，2026-09-22 用户定调）

> SPEC 不是「留文档」，而是把 Agent 从**无状态聊天**变成**有状态施工**：外部记忆 + 执行契约 + 变更边界 + 验收标准 + 审计凭证。

| # | 价值 | 对 Agent 的具体作用 |
|---|---|---|
| 1 | **上下文锚点** | 会话中断 / 换模型 / 换 IDE / 隔几天再继续时，读 SPEC 即可恢复「目标 · 非目标 · 改了哪些文件 · 为什么这么改 · 怎么验收 · 怎么回滚」，不必重新讲背景，也不给 AI 自由补全漂移的空间 |

## 分支纪律（2026-09-22 定稿）

- **一个 Spec 一个分支**（不是每个 commit 一个分支）
- 同时活跃分支 **≤ 2 个，最好 1 个**
- 分支寿命：**1 天内最好 / 3 天可接受 / 超过 1 周必须拆或放弃**
- 合并方式：**squash merge**——master 历史是「一条 Spec 一条提交」，干净可回滚
- 合并后**立刻删本地 + 远程分支**；代码平台开启「合并后自动删除分支」
- 每周 5 分钟清理：`git branch --merged master`（本地）/ 平台已合并分支列表（远程）
- 分支命名：`feat|fix|refactor|audit|docs/SPEC-<ID>-简述`
- 提交信息格式：`type(scope): 描述 [SPEC-<ID>]`

## 远端推送策略（2026-09-22 用户决定）

> 用户原话（逐字）：**「如果github侧不稳定，可以暂时先放弃github每次提交等，等到时候真正完成的时候，进行全量整合批量搬运即可」**

- **GitHub 侧不稳定时不逐次 push**：本地照常按上节纪律 squash 合入 `master`，**阶段性完成（或网络稳定）时一次性批量推送** `git push origin master`。
- 因此 **CI 首跑 / 复跑的验证时点顺延**到那次批量推送之后；在此之前 CI 的等价验证用「**干净克隆复现法**」（`git clone --local` 到 scratch + 项目 venv 跑同款命令）在本地完成。
- 本地 `master` 与 `origin/master` 的差值就是待搬运量，用 `git status -sb` 一眼可见。
- **首次批量搬运（2026-09-23，已完成）**：`2b673fb..290eb9f` → 首跑 `#35800087797` 红 → 修（取证步 + Qt 夹具）→ 复跑 `#35800505406` 红（annotations 定位 A20）→ 修 → **三跑 `#35800786078` success**；全过程留证 `docs/devlog/L3远端首跑留证_2026-09-23.md`。随后 留证提交 `…e863fdd` 再推一次 → `origin/master` 与本地同步（**待搬运量 0**）。
