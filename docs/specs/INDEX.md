## 分支纪律（2026-09-22 定稿）

- **一个 Spec 一个分支**（不是每个 commit 一个分支）
- 同时活跃分支 **≤ 2 个，最好 1 个**
- 分支寿命：**1 天内最好 / 3 天可接受 / 超过 1 周必须拆或放弃**
- 合并方式：**squash merge**——master 历史是「一条 Spec 一条提交」，干净可回滚
- 合并后**立刻删本地 + 远程分支**；代码平台开启「合并后自动删除分支」
- 每周 5 分钟清理：`git branch --merged master`（本地）/ 平台已合并分支列表（远程）
- 分支命名：`feat|fix|refactor|audit|docs/SPEC-<ID>-简述`
- 提交信息格式：`type(scope): 描述 [SPEC-<ID>]`

## 远端推送策略（2026-09-22 用户决定）

- **GitHub 侧不稳定时不逐次 push**：本地照常按上节纪律 squash 合入 `master`，**阶段性完成（或网络稳定）时一次性批量推送** `git push origin master`。
- 因此 **CI 首跑 / 复跑的验证时点顺延**到那次批量推送之后；在此之前 CI 的等价验证用「**干净克隆复现法**」（`git clone --local` 到 scratch + 项目 venv 跑同款命令）在本地完成。
- 本地 `master` 与 `origin/master` 的差值就是待搬运量，用 `git status -sb` 一眼可见。

## 范围外变更请求（RCR）模板

执行中一旦发现需要改 Spec 未列出的文件，**立即停止**并按此格式输出：

```
范围外变更请求
- 触发：正在执行 SPEC-<ID> 的哪一步
- 需要动的文件（Spec 外）：@路径
- 为什么必须动：<根因，不是"顺手优化">
- 不动的后果：
- 最小改法：
- 是否可延后为独立 SPEC：是/否
等待批准：是
```
