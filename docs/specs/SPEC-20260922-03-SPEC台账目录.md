# 建立 SPEC 台账与审计目录

## 目标

让「Spec」从聊天记录里的一条消息，变成**仓库里可以随时打开审计的文件**：

1. 新建 `docs/specs/` 作为 SPEC 唯一存放目录，一个 Spec 一个文件；
2. `INDEX.md` 作为台账（ID/级别/目标/状态/分支/合入提交/日期），并登记待批准清单；
3. 把已发生的历史批次追溯登记成正式 SPEC；
4. 把用户定稿的**分支纪律**与**范围外变更请求（RCR）模板**写进台账，供后续所有执行引用。

## 非目标

- 不执行 SPEC-20260922-01（其 4 个文件 `AGENTS.md` / `docs/agents/*` 仍待批准）
- 不改任何代码、不动 `data/`
- 不迁移 `docs/devlog/`（历史施工记录保持原位）

## 新增文件

| 路径 | 内容 |
|---|---|
| `docs/specs/INDEX.md` | SPEC 台账 + 待批准清单 + 分支纪律 + RCR 模板 + 与其它文档的关系表 |
| `docs/specs/SPEC-20260922-01-断流协议落地.md` | 《断流协议》落地 Spec（v2，待批准） |
| `docs/specs/SPEC-20260922-02-两阶段提交与命令路由.md` | V16.2 + V16.2.1 批次（追溯登记，已完成） |
| `docs/specs/SPEC-20260922-03-SPEC台账目录.md` | 本文件 |

## 接口/数据是否变化

无。

## 测试方式

无代码测试。验证 = `git status --short` 只出现 `docs/specs/` 下 4 个新文件；`docs/specs/INDEX.md` 表格中三个 SPEC 均可点击打开。

## 回滚方式

删除 `docs/specs/` 目录（`git revert <该提交>`）。

## 风险

低。唯一风险是台账与实际状态不同步 → 规则：**每次执行 SPEC 后必须同批更新 `INDEX.md` 的状态列**（写入范围已在索引中标注为常规产物）。
