# 步 7：搜索合并 `SearchService`（B7）

## 目标

把**两条搜索入口各自写的一套检索逻辑**收口成一个 UI 无关的服务 `SearchService`，实现「同一检索能力，单一实现」。

## 现场事实（只读侦察，2026-09-27）

| | 顶栏搜索（`TwinChatApp`） | 历史浮层搜索（`HistoryOverlay`） |
|---|---|---|
| 入口 | `search_box`（`gui.py:1911`，`returnPressed`） | `_search_box`（`gui.py:1493`，`textChanged` + 300 ms 防抖） |
| 检索 | `self.conv_store.search(query, limit=10)`（`:2425`） | `self._conv_store.search(keyword, limit=50)`（`:1579`） |
| 交互 | 清旧高亮 → 无结果走系统条「未找到包含「q」的对话。」；有结果走高亮 + `_locate_message` 跳转 + 逐条列「时间 · sender → preview」 | 空 query 回落 `load_recent()`；无结果走「没有找到与「q」相关的回忆。」；有结果走 `_load_data(results, keyword=…)` 高亮 |
| 数据层 | **同一个** `ConversationStore.search()`（FTS5 快路径 + LIKE CJK 兜底，V10.11） | 同左 |

⇒ **数据层早已统一，分叉在两套 UI 逻辑**（重复的调用/空值/异常兜底/无结果判定）。本 SPEC 只收这一层。

## 设计（含两处需明确的取舍）

1. **新增 `shared/search_service.py`**（UI 无关、零 Qt 依赖，纯逻辑可单测）：

   ```python
   class SearchService:
       def __init__(self, conv_store) -> None: ...
       def search(self, query: str, limit: int = DEFAULT_LIMIT) -> List[dict]:
           """空/纯空白 query → []；store 抛异常 → []（与既有两处兜底行为一致）。"""
   def format_preview(content: str, width: int = 60) -> str:
       """`text[:60] + '…'`（顶栏结果行现用格式）抽为纯函数。"""
   ```

2. **两处 UI 改为调用该服务**（**文案、布局、交互全部不变**）：
   - 顶栏：`self.search_service.search(query, limit=10)`；
   - 浮层：`self._search_service.search(keyword, limit=50)`；
   - 服务实例由 `TwinChatApp` 构造并注入 `HistoryOverlay`（沿用现有 `conv_store` 注入链）。

3. **两处取舍（须在 SPEC 里写明，不留给实现自由发挥）**：
   - **limit 有意保持不同**（顶栏 10 / 浮层 50）：顶栏每条结果都渲染成聊天区系统条，50 条会刷屏；浮层是列表浏览，多给才有用。⇒ **「两处命中一致」的判据定义为「同 query + 同 limit → 结果集与顺序逐条相同」**，而不是强迫两处显示同样多条。
   - **无结果文案保持各用各的**（本批真机门禁=否，不得改用户可见文案）；收口的是**判定路径**（都走服务返回空列表 → 各自渲染）。

## 非目标

- ❌ 不改 `ConversationStore.search` 的 FTS5/LIKE 算法与排序；❌ 不改高亮实现（`highlight_plain_text` / `highlight_hits` / `_load_data(keyword=)` 原样保留）；❌ 不动 UI 文案、布局、防抖时长；❌ 不加新搜索能力（过滤/排序/高级语法）；❌ 不动 `ui/theme.py`（本批无样式改动）。
