# GUI 组件树与状态归属审计（前端架构反向梳理法 · PySide6 版）

## 背景与意图

用《前端架构反向梳理》四维法（角色 / 锚点 / 诊断标准 / 结构化输出），对本项目的 **PySide6 界面层**做一次**只读**架构审计，产出「组件树 + 状态真理源矩阵 + 架构痛点诊断 + 重构基线 Roadmap」，作为后续重构（L2/L3）的施工基准。

与既有 `docs/architecture/逆向架构Spec_V16_2026-09-22.md` 的分工：那份是**通读 Changelog/Git/数据模型**得到的系统级架构与台账；本份是**界面层视角**（组件职责边界 + 状态流转），两份互相引用、不重复。

## 目标

1. 产出 `docs/architecture/组件树与状态归属_V16_2026-09-22.md`，含四部分：

   **A. 组件树与「路由」映射**（Mermaid `graph TD`）
   主窗口 → 页面级（聊天区 / 左导航 / 右侧面板）→ 容器级（带业务逻辑的自定义 widget、浮层）→ 展示级（纯 QSS/QLabel 封装）；每个节点标注 `file:line`。

   **B. 状态归属矩阵**（Markdown 表，≥30 行）
   `状态名 | 作用域(Global/Module/Local) | 真理源(file:line) | 消费方 | 传递方式(engine 引用/Qt 信号/store 读取/参数透传) | 冗余或下沉风险`

   **C. 架构痛点诊断**（Severity 降序 High/Medium/Low）

   把 C 收敛成可逐个立 SPEC 的候选清单（含依赖顺序与真机确认点）。

2. 对**最高风险单文件**（预期 `gui.py`，3831 行）做递进式微观梳理：内部逻辑树（视图展现 / 逻辑处理 / 弹窗隔离三层）+ 状态归位建议（哪些局部状态该下沉、哪些异步逻辑该抽出）+ 重构后目录结构建议。

## 诊断标准（本项目版红线，C 部分的判定依据）

模板里的「300 行 / Prop 超 3 层」是 React 口径，此处换算为 PySide6/Python 等价物：

| 维度 | 红线 | 已实证样例 |
|---|---|---|
| 巨型文件 / 类 | 单文件 >800 行；单类 >500 行；单方法 >80 行 | `gui.py` 3831 行；`shared/state.py` ~1500 行 |
| 「Prop Drilling」等价物 | 同一对象（engine / store / bot）经 ≥3 层参数透传到子 widget | 面板刷新链、`_append_parsed_message` 链 |
| 状态冗余 / 双真源 | 同一事实存在 ≥2 处（存档平铺键 / engine 块 / `world_state` / gui 局部变量） | A1 写读不对称、A2 状态先于结果提交、A3 死状态 |
| 副作用分散 | 网络 / 落盘 / 线程 出现在展示层而非集中层 | `gui.py` 内 `_save_state`、`LLMWorker` 线程、取证写入 |
| 死代码 / 空壳 | 入口存在但无实现；同名覆盖 | A9 重复 `_handle_command`；左导航 7 项中 4 空壳 |
| 硬编码真源 | 文案 / 场景名 / 事件池写死源码且多处各一份 | B1–B5：事件×天气 4 套判定、`SCENE_CN` 3 份、`EVENT_POOL` 33 条 |
